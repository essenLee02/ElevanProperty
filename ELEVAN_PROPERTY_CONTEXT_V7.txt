>> BACA INI DULU — TIGA HAL YANG PALING SERING MENYESATKAN <<

  1. CEK JALUR PRODUKSI SEBELUM MENDIAGNOSIS APA PUN.
     Ada DUA basis kode qualification yang MIRIP tapi TERPISAH:
       • services/aiPromptBuilderService.js   → jalur LLM (Claude/ChatGPT/…)
       • controllers/chatbotPrivateController.js → Private Agent (FALLBACK)
     `AI_PRIMARY_PROVIDER=kimi` berarti PRODUKSI memakai jalur LLM via
     aiPromptBuilderService (nilai contoh saat ini; cek .env aktual — provider
     berubah-ubah antar sesi, JANGAN diasumsikan dari dokumen ini).
     Memperbaiki Private Agent tidak akan mengubah apa pun yang dilihat
     customer. Sudah berkali-kali diagnosis salah arah karena ini (M52, M54).
     Verifikasi: `grep AI_PRIMARY_PROVIDER backend/.env` + log runtime
     `[WhatsAppAI] Calling AI provider: { primaryProvider: … }`.

  2. STATE SELALU DARI HISTORY PENUH — JANGAN PERNAH DIPOTONG.
     `extractQualificationState()` dipanggil DI DALAM buildWhatsappReplyPrompt.
     Memotong `history` sebelum memanggil builder = memotong input state =
     seluruh field jadi null pada percakapan panjang = loop tanya-ulang tanpa
     akhir (M64, pengulangan M35). Pemotongan token HANYA boleh mengenai
     transkrip yang DITAMPILKAN (`AI_PROMPT_DISPLAY_TURNS`, default 20).

  3. MENAMBAH ATURAN PROMPT ADA HARGANYA — PAKAI EKSTRAKTOR KODE SEBALIKNYA.
     Prompt WhatsApp per pesan ±53–56K token; limit TPM bervariasi per
     provider (mis. gpt-4o-mini org 60.000/menit). Tiap aturan baru
     memperburuk rasio sinyal:derau dan menurunkan kepatuhan model secara
     global (M62). Bila sebuah loop bertahan MESKIPUN DIREKTIF FINAL sudah
     benar → yang kurang adalah EKSTRAKTOR (kode), bukan aturan prompt.
     ⚠️ PENGECUALIAN (dipelajari di V7/M83): bila server state SUDAH
     null/clean tapi LLM tetap MENGARANG nilai di summary, itu BUKAN bug
     ekstraksi — model mengabaikan "never invent". Di kasus itu perbaikannya
     adalah CONTOH KONKRET before/after dari kegagalan produksi (bukan aturan
     abstrak tambahan) di buildFinalDirective() + skill docs.


>> PERUBAHAN BESAR V6 → V7 (3 Agu → 4 Agu 2026): MALANG TRANSCRIPT BATCH <<

  1. DEBOUNCE RACE CONDITION — ROOT CAUSE DARI Q6/Q7 REPEATED-QUESTION STORM
     Produksi, 4 Agu 2026 (Malang hotel booking): pelanggan melihat 3–4 balasan
     AI berbeda dalam rentang <2 menit, termasuk satu pesan terputus di tengah.
     Root cause: responseDebounce.js menghapus _pending[key] SEBELUM memanggil
     async onFire() (AI provider bisa makan beberapa detik). Pesan customer
     yang tiba saat onFire PERTAMA masih berjalan membuat batch/timer
     INDEPENDEN KEDUA → dua panggilan AI paralel untuk sesi sama, membaca
     state snapshot berbeda, keduanya terkirim.
     Fix: per-key promise-chained mutex (_inFlight map) sehingga onFire[key]
     tidak pernah berjalan paralel; batch baru menunggu batch lama selesai.
     Regresi: tests/responseDebounceConcurrency.test.js (4/4, termasuk kontrol
     negatif bahwa key BERBEDA tetap boleh concurrent).

  2. VIEWINGDATE DARI KALIMAT AI SENDIRI — FALLBACK UNTUK KASUS DEKLARATIF
     Q9b/Q9c detection: AI sering MENYATAKAN tanggal dalam pertanyaan jam di
     KALIMAT SAMA ("...jadwal survei di tanggal 18 Agustus 2026, kira-kira jam
     berapa yang paling pas?"). Pola "tanggal berapa" interrogatif tidak
     match → viewingDate jatuh ❓. Customer jawab "Jam 2 siang" saja, summary
     menampilkan "Viewing: Besok siang jam 2" (besok = fabrikasi LLM).
     Fix: parseCustomerDate() fallback pada ai.message sendiri ketika
     aiAsksViewTime match tapi viewingDate masih null.
     Regresi: tests/viewingDateFromAiStatement.test.js (6/6).

  3. ANCHORPOINT (Q6) OVERWRITE GUARD — LINDUNGI JAWABAN BAIK DARI RE-ASK
     Q6 diulang karena debounce race (item 1). Tiap ulangan bisa menimpa
     jawaban "baik" sebelumnya dengan "Tdk ada" tanpa guard.
     Fix: (!state.anchorPoint || CORRECTION_RE.test(custResp)) — hanya ralat
     eksplisit boleh menimpa.
     Regresi: tests/anchorPointOverwrite.test.js (6/6).

  4. DISTRICT DARI Q6 "DI X" ROUTING — JANGAN HILANG SAAT ANCHORPOINT ADA
     Jawaban Q6 "Di Dinoyo" sering kali maksud customer = area, bukan
     landmark. Deteksi berpasangan lama membuat district-routing jadi dead
     code (nested di dalam anchorPoint guard) begitu Phase 1 sudah men-set
     anchorPoint dari jawaban Q5 terpisah ("dkt pasar, dkt mall").
     Fix: dipindah ke if-block INDEPENDEN, gated hanya (!state.district).
     Regresi: sama file, tests/anchorPointOverwrite.test.js (6/6, mencakup
     kasus ini juga).

  5. SELF-VOLUNTEERED DURATION — TIDAK PERLU DITANYA JIKA DISEBUTKAN DULUAN
     Kasus: "Rencana checkin 2 minggu lagi, Kak. Durasi sewa 5 hari" — satu
     pesan, dua unit berbeda (offset tanggal vs durasi sewa). Ekstraktor lama
     hanya jalan saat AI bertanya "berapa lama" (AI-gated), sehingga durasi
     yang disebut duluan hilang dan tercampur dengan offset tanggal.
     Fix: extract duration SEBELUM ekstraktor AI-gated, anchor KETAT pada
     kata "durasi" supaya tidak mengambil angka dari offset tanggal terpisah.
     Regresi: tests/durationDateConflation.test.js (6/6).

  6. SUMMARY ANTI-HALLUCINATION — CONTOH KONKRET > ATURAN ABSTRAK
     Transkrip Malang, summary yang terkirim ke agent memuat:
       • Area: "*kota Malang\nKamar yang standard*" ← field ganda (garbled)
       • Durasi menginap: "2 minggu" ← SALAH (ambil offset tanggal, bukan
         durasi — lihat item 5)
       • Keputusan bersama: "*Iya, Kak\nSaya survei bersama istri*" ← fabrikasi
       • Patokan lokasi: "Bebas" ← hilang (overwrite bug, lihat item 3)
       • Viewing: "Besok siang jam 2" ← kata relatif (halusinasi, lihat item 2)
     Dibuktikan lewat reproduksi bahwa SEMUA state di server sudah bersih —
     ini BUKAN bug ekstraksi, LLM mengabaikan instruksi "never invent".
     Fix: buildFinalDirective() bagian "Summary Strict Rules" + skill doc
     04-qualification-flow.md item 11–14 diberi CONTOH KONKRET before/after
     per field (one-line value; Area≠Kota; Keputusan bersama TIDAK boleh
     fabrikasi dari Q9 kosong; Viewing = tanggal absolut, bukan "besok").
     Disinkronkan ke claude_responds, chat_gpt_responds, elevan-property-
     assistant.

================================================================================
  1. OVERVIEW
================================================================================

Elevan Property = platform manajemen properti berbasis web + AI chatbot WhatsApp
multi-agent untuk pasar Indonesia. Menghubungkan agen properti dengan calon
pembeli/penyewa lewat WhatsApp, memakai AI untuk mengkualifikasi kebutuhan
customer secara otomatis (Q1–Q14), lalu menghasilkan brief/rekomendasi.

Konsep inti:
  - Website + floating chatbot pencarian properti (publik, tanpa login)
  - WhatsApp chatbot multi-agent: tiap agent punya nomor/device sendiri
  - AI 6-opsi: satu PRIMARY (via env, mis. `kimi`) → Private Agent
    (deterministik, selalu ada sebagai fallback)
  - Qualification flow Q1–Q14 SELALU jalan; RESPOND_CATALOG_RUN hanya
    mengontrol apakah katalog ditampilkan SETELAH summary
  - Data properti: DB (per-agent) + JSON fallback + Rumah123 live (opsional)
  - Landmark: peta kurasi 45 kota + Google Places live (dorman, billing off)
  - Admin dashboard: CRUD Country/Province/City/Location/Facility/Property/
    Customer (7 modul)

Pengguna:
  - AGENT   : kelola katalog & percakapan sendiri; bisa takeover AI per-customer
  - CUSTOMER: chat via WhatsApp, dikualifikasi AI, terdaftar otomatis
  - ADMIN   : master data & monitoring

Deployment:
  - Frontend : https://propmatches.netlify.app (Netlify)
  - Backend  : Node.js port 5055 (ngrok auto-start untuk dev webhook)
  - Database : MySQL `db_property` (Sequelize ORM v6)
